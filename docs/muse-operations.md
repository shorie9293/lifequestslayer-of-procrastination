# 駿麒（Muse）運用ガイド — LifeQuest を触らせるための手順

対象: Meta のエージェント **Muse**（個体名 **駿麒**）。GitHub コネクタ経由でこのリポジトリを読み書きさせる。

## 0. 前提（Muse の GitHub コネクタの限界）
| できる | できない |
|--------|---------|
| ファイル内容の読み取り | コミット履歴・ブランチ・タグの操作 |
| テキストファイルの書き込み（`push_files`＝スナップショット） | バイナリ（画像・zip・フォント）の書き込み |
| 指定ブランチへの一括反映 | ファイル削除の反映（消しても残る） |

→ **必ず作業ブランチ `muse/work` に書かせ、PR で受ける。main を直接触らせない。**
→ 受け入れ時に `git diff --stat` と削除漏れを人力確認する（1分で済む）。

## 1. 創造主様の作業（初回のみ・3分）
1. Muse のアプリで GitHub コネクタを接続し、対象リポジトリ `shorie9293/lifequestslayer-of-procrastination` を許可する。
2. 書き込み権限（Contents: Read and write）を付与する。
3. Muse の Identity → Soul に下の「Soul 追記ブロック」を貼る。
4. 下の「動作検証3問」を送る。

> コネクタ権限は高天原側からは付与できない（Muse 側の設定）。ここだけは創造主様の手が必要。

## 2. Soul 追記ブロック（コピペ用）
```
## 開発の掟（LifeQuest / 延鬼討伐伝）

### 優先順位
リポジトリの AGENTS.md > このファイル > 会話中の指示。矛盾したら AGENTS.md に従い、1行で報告する。

### 0. 作業前に必ず読む
AGENTS.md → SPEC.md → docs/decisions.md → docs/roadmap.md の順に読む。読まずにコードを書かない。
振る舞いを変える前に SPEC.md を更新し、差分を1行で示す。

### 1. TDD
失敗するテストを先に書く → 最小実装で通す → 整理する。順番を飛ばさない。
テストが無い機能を「実装した」と言わない。

### 2. 報告は証拠のみ
「動作確認しました」禁止。実行したコマンドと出力（テスト件数・失敗0・exit code）を貼る。
未検証は「未検証」と明記。完了報告は3行：①できるようになったこと ②テスト結果 ③残る制約。

### 3. デバッグ
同じエラーで2回失敗したら手を止め、原因を1行で特定してから進む。バージョン番号の連打を禁止。

### 4. 設計と依存
データモデル・状態管理・永続化・認証・外部API・依存追加は、実装前に触るファイルを列挙して確認を取る。
秘密情報はコードに直書きしない。

### 5. リポジトリ
1コミット1目的。main へ直接書かない（作業ブランチ muse/work に書く）。
削除したファイルは削除したと報告する（コネクタは削除を反映しない）。
変更後は flutter analyze --no-fatal-infos と対象テストを通す。赤いまま終えない。

### 6. このリポジトリ固有
- pubspec.yaml の version を上げると main マージで Play へ自動デプロイされる。勝手に bump しない。
- 新しい test/features/<name>/ を足したら .github/workflows/flutter-ci.yml のシャードにも追記する（無いと CI で走らない）。
- ../../packages/ の path 依存があるため、単独 pub get の失敗は環境要因。CI と同じ手順で確認する。
```

## 3. 動作検証3問（効いているかの判定）
1. 「hi」→ **1行**で返れば人格ルールが効いている。長い自己紹介＋提案リストなら効いていない。
2. 「このリポジトリの AGENTS.md を読んで、守るべきルールを5行で」
   → 読めないなら GitHub コネクタの権限不足。
3. 「docs/roadmap.md の未完了項目から、テストだけで完了できるものを1つ選んで実行して」
   → 報告が「3行＋証拠」形式になっているか確認。

## 4. 最初に任せる実務タスク（推奨順）
| 順 | タスク | 理由 |
|----|--------|------|
| 1 | `docs/roadmap.md` の未完了項目を一覧化し、重要度×修正コストで並べる | コードを壊さず、理解度を測れる |
| 2 | 空状態・エラー状態が無い画面を列挙する（修正はしない） | AGENTS.md §5 のチェックリストを実行させる |
| 3 | 最も小さい1件を SPEC.md → テスト → 実装 の順で直す | TDD の順序を守れるかを見る |

## 5. 受け入れ（創造主様 or 高天原側）
```bash
git fetch origin muse/work
git diff --stat origin/main...origin/muse/work      # 変更範囲
git diff origin/main...origin/muse/work -- '*.dart' | head -200
flutter analyze --no-fatal-infos
flutter test --no-pub -j 1 test/<触ったfeature>/
```
- 差分が AGENTS.md の範囲（1コミット1目的・無断の依存追加なし）に収まっているか
- 削除されたファイルが無いか（コネクタは削除を反映しないため、逆に「消したつもり」を検出する）
- 緑なら `gh pr merge --squash` で合祀。

## 6. 戻し方
- 人格リセット: 「Go back to your default personality.」
- 個別ルール削除: Soul から該当行を削除。
- 事故時: `git revert <merge commit>` で1コミットで戻る（squash merge 推奨の理由）。
